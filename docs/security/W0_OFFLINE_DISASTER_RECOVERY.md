# Offline disaster recovery — ODR candidate

Status: engineering candidate, not operational authorization. No actual owner keys, physical media, database or recovery device were accessed. Preserve existing W0 acceptance baseline e076b678fd842f0a88f21da26e34303335b5712f and CI 45901831568.

## Threat model and limits

- An independently held, cryptographically random 256-bit recovery secret (64 hexadecimal characters) encrypts a small versioned HBR1 envelope using AES-256-GCM, a random 96-bit nonce and domain-separated authenticated header. This is a random key, NOT a human password; syntax cannot prove entropy. Use an owner-approved offline random generator or password manager on a trusted device. No recovery secret is accepted in argv, environment or logs by production commands.
- One bundle covers one explicit historical backup AES key ID and checkpoint Ed25519 public-key ID. Maintain a bundle and independently recorded PUBLIC SHA-256 fingerprint for every retained key pair. The public fingerprint is checked out of band; never trust a fingerprint from the untrusted manifest or bundle itself.
- No signing private key, MFA encryption key, Django signing secret, emergency owner key, password or session data is escrowed. The recovery provider has no active/signing methods. Replacement-device signing rotation, employee MFA re-enrollment and GM recovery are separate existing or future owner-approved workflows. No account activation or database installation is implemented here.
- A stolen bundle plus its recovery secret can decrypt backups covered by that key; keep bundle, recovery secret and backup on distinct owner-controlled offline custody locations. Loss of all copies means loss of access. No automatic export, retention deletion, schedule, or vault import. Python process memory cannot guarantee secure zeroization; encrypted workspace/disk and trusted OS remain required.

## Owner-only issuance on source

From the actual source installation, locally and interactively, use manage.py create_backup_recovery_bundle --destination ABSOLUTE_EXTERNAL_PATH --encryption-id ID --signing-id ID with the normal authorized settings. The command checks physical/local console policy, current singleton GM emergency owner key (not consumed), independent secret and confirmation, configured key provider, schema and full chain; writes only an exclusive encrypted artifact and audits its digest. No keys are printed; the public fingerprint and artifact digest are safe to record out of band. If audit commit fails after publication, retain artifact securely and investigate; no success claim. Use explicit retained historical IDs, never silently fall back to current IDs.

## Clean-room disposable verification

Use a clean trusted checkout of the compatible verifier, an encrypted temporary workspace and a local interactive terminal. From backend, with DJANGO_SETTINGS_MODULE unset, run python -m security.offline_recovery_cli --vendor sqlite --backup PATH --checkpoint PATH --bundle PATH --trusted-public-sha256 PUBLIC_FINGERPRINT. For PostgreSQL use --vendor postgresql --isolated-postgres --pg-port PORT --pg-user ROLE on an isolated loopback-only recovery instance, not a production server. Enter recovery secret and isolated PostgreSQL password interactively. The standalone process uses Django dummy ORM backend; it does not query an ERP account or use source credentials. Explicit engine matching, pinned public trust, authenticated bundle, signed manifest, ciphertext digest, authenticated decrypt, disposable restore, full chain/guards and cleanup are mandatory. PostgreSQL dumps execute database objects; only restore authenticated trusted backups in a restricted isolated instance. Physical isolation and role permissions must be verified by owner, not assumed by flags.

Successful verification does not install the restored DB or create a GM session. Never point the tool at production infrastructure, never overwrite a live database, never treat temporary files as securely erased. A separate activation and disaster recovery drill must establish account recovery, new vault provisioning, preserved financial balances, new signing authority, replacement-device operational acceptance and RPO/RTO. Actual deployment topology, two independent backup media, key custody, retention/scheduling and recovery location remain owner decisions.

## Final recovery groundwork candidate — unique key generations and independent manifest selection

Fresh Windows vault provisioning uses random 128-bit suffixes on MFA, backup encryption and checkpoint signing key IDs. Existing vault reads still resolve their stored IDs, including legacy fixed IDs; provisioning refuses existing or partial vaults. Active pointers are reserved before new key material is written so an interrupted process leaves a detectable partial vault; no automatic overwrite or repair. Use only a clean authorized Windows account/device with the normal provisioning commands, never a live source vault. Historical backup decryption and public verification still use the separate recovery bundle for their exact historical IDs; new vault keys are not substitutes.

Record the exact **backup checkpoint SHA-256** returned by successful backup issuance independently of the backup, bundle and public-key fingerprint, as the owner-selected recovery point. The disposable offline CLI accepts `--trusted-checkpoint-sha256` and checks the same bytes it authenticates, rejecting mismatched signed older manifests before decryption. Without this independent pin the CLI remains a disposable verification tool and explicitly reports that freshness is unverified. A matching pin proves selection, not that the chosen backup is the latest or that its GM emergency key was not later revoked. A future activation gate must require independent current owner-controlled evidence, reject unresolved rollback, and require explicit source-device isolation. Do not derive this pin from the candidate manifest during recovery. No activation command, credential bypass or automatic restore publication is added here.

New tests cover distinct real Windows vault generations, legacy reads/no-overwrite, valid signed old-manifest rejection, malformed selection pins and CLI integration. Execution pending. Global session retirement, employee MFA re-enrollment, comprehensive reconciliation, fail-closed activation and physical owner acceptance remain open.

If rollback cleanup itself fails, retain active pointer records for detection and refuse further provisioning; manual inspection of the protected vault is required. A Windows test injects both a provisioning write failure and a cleanup failure.


## Recovery readiness report — read-only engineering candidate

Add `--readiness-report` to the standalone disposable recovery CLI together with the independently recorded `--trusted-checkpoint-sha256`. The tool checks all POSTED/REVERSED journal totals against their one-sided lines, verifies stock movement direction and running quantities in posting ID order per product/warehouse, and checks existing party ledger attribution account/status. It reports counts only (including idempotency records, cash-account masters, historical registry/Django sessions, MFA devices/policies, unused recovery codes and owner-key rows); no personal details, financial line contents or credentials are printed. The report does not assert cash balances, inventory valuation, all subsidiary ledger completeness, full source-to-restore reconciliation, current owner-key validity, or authorization to activate. Missing or inconsistent data blocks the readiness report without mutating or repairing anything. SQLite numeric representation can limit exact stored-decimal verification; discrepancies require investigation, never automatic rounding correction.

### Owner-controlled recovery decision checklist (not an activation command)

1. Keep source device and any copies offline and under owner custody; do not allow concurrent writers. If isolation is uncertain, do not resume business operations. Software on one offline device cannot prove another is off.
2. Select the latest independently recorded successful backup/manifest digest and trusted public fingerprint; account for any later emergency-owner-key rotation or consumption. If independent freshness evidence is missing, stop. A valid old signature is insufficient.
3. Verify a disposable restore with the readiness report in isolated storage. Investigate every mismatch; compare actual trial balance per currency, party balances, warehouse stock and valuation, cash/payment balances, allocations and open documents against independently retained business reports. No automatic correction.
4. Keep recovered database unpublished. New Windows vault provisioning must be on the dedicated replacement OS identity. Do not overwrite historical keys, disable required MFA, reuse old Django signing secrets, or use old recovery codes to evade owner-approved re-enrollment. Global session revocation and secure employee MFA recovery are still engineering blockers.
5. Record actual media custody, backup schedule/retention, recovery-point/time objectives and physical replacement-device drill with owner approval. No production publication until all engineering and operational gates pass. No automatic retention deletion.

Tests: extend real offline CLI recovery on both database engines to check the report with two stock movements and historical session fixtures, and add signed-but-inconsistent journal rejection/cleanup. Actual CI pending. No new dependencies, migrations, services, production database publication or change to normal financial operations.


## Replacement identity staging candidate

The local-only internal service `security.replacement_identity` prepares credentials inside an explicitly isolated, unpublished database. It requires the dedicated staging process flag, local console, explicit source-isolation attestation, independently authenticated expected audit chain and independently recorded latest owner-key row ID, plus the existing raw owner key. It refuses historical MFA key IDs and an outer transaction. GM recovery, global registry session retirement, removal of historical Django session rows, retirement of all old non-GM MFA devices/codes and aggregate audit evidence commit together. Required employee MFA policies and roles are unchanged; required employees cannot log in until re-enrolled. Employee re-enrollment requires fresh recovered GM password/TOTP, employee password and new TOTP, a previously retired device and no live sessions. No API or production command exposes these internal primitives. Real disposable restore test exercises this candidate on both engines, including failed independent prerequisites, audit rollback, source unchanged, wrong employee password and replay denial. Console and key-provider boundaries remain synthetic.

This does not establish that the source is physically offline, that independently supplied owner/checkpoint evidence is current, or that the restored database is authorized for activation. BasicAuthentication compatibility for non-MFA staff remains the frozen contract. A staging orchestrator and physical owner acceptance are still required; never point these services at the live ERP. Full external business report reconciliation, staging publication, custody and recovery drill remain open. CI pending; no release, merge, freeze or production activation.
